# Security and operational boundaries

Financial mutations use PostgreSQL serializable transactions with bounded serialization/unique-conflict retry. Member liability summary must match immutable postings at commit; entry insertion is limited to the transaction that created its header. Double-entry checks are deferred because both entries must exist at commit. Positive integer amounts, wallet balances bounded at the owner-approved THB -50 floor (negative debit requires explicit POS approval and immutable before/after snapshots) and unique request/event/provider references are database constraints. Use explicit debit/credit, not signed floating point values.

Database owner/superuser can disable triggers: production application must not use an owner credential. Migrate with a separate privileged role; grant runtime only needed SELECT/INSERT/UPDATE permissions, no DDL/TRUNCATE or ledger/audit DELETE/UPDATE. Audit actor strings such as provider:sandbox distinguish system actors. Do not log raw request bodies, OTPs, bearer member tokens, OAuth tokens or secrets. The adapter strips Google access, refresh and ID tokens before account linking; only the provider subject and account identity are retained. Limit database access and encrypt at rest.

Account status/role is checked server-side. Public inputs cannot set roles or verified phone status. Admin routes remain disabled pending independent MFA implementation. Email OTP to Google email is not an independent factor. Session uses Auth.js database strategy with HttpOnly SameSite cookies and secure cookies under HTTPS; local HTTP is development only. User-facing financial pages use dynamic server rendering and no-store APIs. No wallet authorization from cache, localStorage, browser math or offline service worker. Wrong OTP attempts commit even when verification fails. Redis rate limiter fails closed. OTP sending can fail after creating a challenge; failed delivery invalidates it, provider timeout still requires cooldown before resend.

Member tokens are short-lived, opaque and single-use; they remain bearer credentials and an attacker with a currently valid screenshot can race the member. Single use and expiry stop old screenshots, not real-time theft. High risk payments require a future member approval/challenge policy. Scanner/device trust, terminal provisioning and authenticated reader bridge remain production work.

POS error recovery saves the pending payload and original key in sessionStorage, scoped to the staff user, and restores it after same-tab reload. The bearer member token is retained only until confirmed completion or a definite rollback error. Closing the browser/tab or clearing storage can lose this state; a durable reconciliation UI remains a release blocker. Supervisor refund endpoint must be limited to trusted supervisors; employee proposals and separate approval workflow remain future work. No manual adjustment endpoint exists.

Production hardening: test OAuth CSRF/state/PKCE and cookies with real Google; tighten CSP after browser tests; request-size limits at ingress, webhook rate/abuse controls, provider signature timestamp validation, secret rotation, role revocation/session invalidation, monitoring, dependency audit and locked versions. Outbox for reliable notifications and payment exception reconciliation still required. Do not represent this foundation as a completed security audit.
